## 一、结论摘要

| 需求点 | 结论 |
|---|---|
| 1 匀色算法 | 主推"重叠区全局辐射平差（景级增益/偏置，最小二乘）+ 分块 Wallis 局部精化"；直方图匹配保留为可选（你已熟悉，作为对比/回退方案）。OpenCV 无直接匀色 API，GPU 版本存在但本机无 NVIDIA GPU，本期按"CPU 多线程 + SIMD"设计，GPU 仅作编译开关预留（`IP_ENABLE_GPU`，默认 OFF）。**经完整评估（§3.6）本项目不引入 OpenCV 依赖**：本项目负载为直方图统计/逐像素映射/重采样与编码（交 GDAL）/小规模 LS，OpenCV 三大优势（imgproc 滤波、稠密线代、CUDA）均未被使用 |

### 2.2 测试数据分析（本次实测）

**2024 年数据（4 景，H48E018/019_014/015C）**
- EPSG:**4490**（CGCS2000），13912×9279，分辨率 ≈2.0m，RGB+Alpha，COG 布局 + WEBP 有损(level 85)
- 4 景全有效（100%），呈 2×2 阵列分布，景间存在窄重叠（约 46m×18.6km 与 27.9km×40m，约 23×20 像素）
- **景内色差明显**：R 通道均值 81.3 / 95.4 / 88.9 / 93.7 —— 同批次仍需匀色

**2025 年数据（GF2_PMS1）**
- EPSG:4490，40053×34426，分辨率 ≈0.8m，RGB+Alpha
- **有效像元仅 66.9%**（约 1/3 为 alpha=0 无效区）
- **极暗**：RGB 均值仅 23.3 / 25.3 / 18.7（对比 2024 的 81~97，差 3~4 倍）——这是"切片后瓦片颜色不一致"问题的直接来源

**两组数据重叠**：约 32km × 27km 大范围重叠 → 非常适合做重叠区统计匀色，也是理想的算法测试场。

**z18 白瓦片问题的量化判断**：Web Mercator z18 在北纬 29° 分辨率 ≈0.52m/px。2024 数据(2m)过采样 4 倍、2025(0.8m)过采样 1.5 倍。**过采样只会"糊"，不会"白"**；白色的最可能根因是 GF2 的 33% 无效区在切片时未被正确声明（alpha=0 未参与处理、或背景值 255 被当作有效数据、或 JPEG 输出无透明通道）→ 见 3.5 节，Phase 0 复现验证。

## 三、技术调研结论（问题 1~5 逐项）

### 3.1 匀色算法选型（需求 1）

**行业实际在用什么**（调研：ArcGIS 文档、PixelGrid/OrthoVista 资料、武大 2024 综述、Frontiers 2025 论文）：

| 算法 | 工业地位 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| **重叠区增益/偏置全局平差**（radiometric adjustment） | 大区域镶嵌生产主流（ISPRS 2024/武大 2024 框架） | 景级一次解算、无逐对误差累积、可并行、物理意义清晰 | 需重叠区 | **主推** |
| **分块 Wallis 滤波**（含逐像元距离加权变体，专利 CN109300083A） | 国产生产软件主力（PixelGrid 等） | 景内亮度/反差不均也能处理、保纹理 | 分块不当有块效应 | **主推精化步骤** |
| 直方图匹配 | ArcGIS 色彩平衡选项之一，经典 | 简单鲁棒、你已有实现 | 全局映射，可能破坏辐射、重叠小/无重叠时失效 | 保留为可选方法 |
| Reinhard 颜色传递 / Monge-Kantorovich 最优传输 | 学术为主 | 分布匹配更完整 | 计算重、工程化少 | 进阶可选（后期） |
| 深度学习（SECBNet、CA-CycleGAN 等） | SOTA 但工业落地极少 | 自动化程度高 | 需训练数据与算力、不可控 | **本期不做**，列入远期 |

**推荐方案（两级流水线，经 Phase 0 修订）**：

```
第 0 步（新增，前置）：接边一致性检查
  量测所有重叠影像对的 Δμ/Δσ（重叠区统计），
  |Δμ| < 阈值(默认 2) 的景对自动跳过调节 —— 已接边连续的数据不做任何改动。
  （Phase 0 教训：对本来就接边连续的标准图幅做全局统计对齐，
   会在接缝处制造 -6~-14 的亮度台阶，见 Phase0验证报告.md §4）

第一级（景间）：重叠区辐射平差（主方法，唯一硬约束=重叠区一致性）
  在每对重叠影像的重叠区分别统计两景的 (μ, σ)（逐波段），
  建立每景每波段的线性模型 DN' = a·DN + b，
  以"重叠区调节后一致"为约束做链式/最小二乘图平差。
  参考 target：可指定参考影像 / 用户给定目标 (μ,σ) 作为弱正则。
  禁止：仅用景的全局统计互相对齐（会破坏接边连续性）。
  无重叠的特殊场景（如新批次与基准批次无任何空间重叠时的视觉统一）才允许全局目标，且需提示接缝风险；
  跨批次若有重叠，同样以重叠区统计解参（Phase 0 §4.6 实测：全局目标留 -4.1 残差）。

第二级（景内，可选开关）：分块 Wallis 精化
  分块统计 → 参数网格 → 双线性插值得到逐像元 (a(x,y), b(x,y))，
  消除景内亮度趋势（专利 CN109300083A 思路），消除分块效应。
  局部统计天然保形，Phase 0 实测接缝台阶 +0.56（全局平差为 -6.23）。

镶嵌兜底：重叠区羽化（feathering）线性过渡，属于镶嵌 operator 职责。
```

- 数学上第一级是第二级的退化形式（整景一组参数），两级可统一为"参数场"实现。
- **OpenCV 的角色（复核后修订，见 §3.6）**：cv::calcHist / LUT / 矩阵运算理论上可承担统计与映射，但**本项目的等价实现为自研代码 + GDAL**，且经评估 OpenCV 在此不占优（统计需先整理为 Mat 并处理掩码、LUT 环节非瓶颈）→ **定稿：不引入 OpenCV 依赖**（vcpkg.json 与 CMake 均不含）。
- **OpenCV GPU**：`cv2.cuda` 有 calcHist（仅单通道 8bit）、LUT 等，需 `opencv4[cuda]` 编译（需本机 CUDA Toolkit）。匀色本质是"一次统计 + 逐像素 LUT 映射"，属带宽型负载，大图 GPU 收益存在（cuCIM/CV-CUDA 有成熟算子）。但**本机无 NVIDIA GPU** → 本期 CPU 多线程 + AVX2 为主，GPU 作为编译开关预留（`IP_ENABLE_GPU`），收益留待有 GPU 的环境验证。

### 3.2 切片技术选型（需求 2）

**GDAL 最新能力（2026-10 官方文档确认）**：

- `gdal raster tile`（3.11 新增，C++ 实现，gdal2tiles 自 3.13 弃用并重映射到此）：
  - **内建多线程**：`-j/--num-threads`（默认 ALL_CPUS）、`--parallel-method thread|spawn|fork`（3.12 新增）—— GDAL 对多线程切片**已友好**，"GDAL 并行不行"是旧印象；
  - 输出 PNG（默认）/ JPEG / WEBP / COG；`--tile-size` 可自定义（默认 256）；
  - nodata 处理参数齐全：`--excluded-values`、`--excluded-values-pct-threshold`、`--nodata-values-pct-threshold`、`-x`（跳过全透明瓦片）、`--add-alpha` 等；
  - **自定义 TMS**：OGC TileMatrixSet JSON 放入 GDAL data 目录即自动识别（`tms_XXXX.json`）→ 4490 方案可插拔实现。
- **GPU：GDAL 已无任何 GPU 能力**（OpenCL warper 3.11.1 已移除，无 CUDA 集成）→ GPU 只能自研（OpenCV CUDA / CV-CUDA / cuCIM），且仅对重采样/编码/匀色映射有意义。
- **Warp API 多线程**：`GDALWarpOptions::NUM_THREADS` + `ChunkAndWarpMulti`（I/O 与计算交叠）；RFC101（3.10+）`GDAL_OF_THREAD_SAFE` 获取线程安全只读 dataset（内部每线程独立打开，有开销）——**自研多线程切片的官方正确姿势**。
- 自研引擎与直接调 `gdal raster tile` 的取舍：CLI 不便嵌入动态库、无法插入匀色钩子与进度回调、TMS 需要落盘 JSON；**自研核心循环（VRT/Warp + 线程池 + 编码），复用 GDAL 全部底层**，工作量可控。

### 3.3 EPSG:4490 切片（需求 3 相关）

- 天地图/国家平台 CGCS2000 方案：EPSG:4490，256×256，z1 级全球 2×1 瓦片（分辨率 0.703125°/px），**层级从 1 起算**（与 WorldCRS84Quad 的 0 起算整体差 1）。
- GDAL 无内建 4490 方案，但支持自定义 `tms_cgcs2000.json`（OGC 17-083r4 标准格式）→ 我们随库分发一份该 JSON（放程序 data 目录，`GDAL_DATA` 或 `GDAL_TMS_SEARCH_PATH` 定位）。
- 4490 与 4326 椭球差异仅 cm 级，**不影响瓦片格网划分**；区别仅在 CRS 声明与层级编号起点。

### 3.4 与超图 / ArcGIS 对比（需求 4）

| 维度 | ArcGIS | 超图 SuperMap | 我们（自研 C++） |
|---|---|---|---|

### 3.5 无效值与白瓦片（需求 5）

**z18 白色的根因分析**（按可能性排序）：
1. **nodata/背景值未声明**：GF2 有 33% alpha=0 区域。若切片时 alpha 未参与（或数据源把无效区写成 255 白），这些区域输出为白色瓦片/白块。ArcGIS 的典型坑：Display Background Value 未设为 NoData、输出 JPEG 无透明通道（Esri 有专门"移除白色背景"工作流，佐证此问题普遍）。
2. **卷积重采样污染**：bilinear/cubic 在有效/无效边界混入无效像素 → 白晕。GDAL 的处理：卷积核内有效像素不足时目标记为 nodata。
3. **瓦片与影像边界部分相交**：影像外区域被填为背景色（未开 `--nodata-values-pct-threshold` 类逻辑时）。
4. 分辨率不足（over-zoom）**只导致模糊，不导致白色**——已量化排除为主因。

**对策（参数化，默认透明）**：
- 切片输出带 alpha 的格式（PNG/WEBP）时：无效区 → 透明；JPEG 时：无效区 → 用户指定填充色（默认白）或建议改格式；
- `nodata_pct_threshold` 参数：整块瓦片无效占比超阈值（默认 100%）→ 不生成/生成全透明，边缘瓦片自动整体透明（阈值可调，如 50%）；
- 可选"采样填充"模式：对必须不透明的场景（如某些发布平台要求 JPEG），用最近有效像素/反距离加权填充无效区（作为后期增强项）。
- **Phase 0 用本地 GF2 数据直接复现白色问题并验证对策**（见 6.1）。

### 3.6 OpenCV 必要性分析（2026-10-13 复核新增）

> 需求 1 曾提出"利用 OpenCV（矩阵运算/算法、可否 GPU）"。本节以**当前已实现的实际计算负载**为准，逐项评估 OpenCV 是否必要，给出定稿结论与再引入条件。

**逐负载评估**

| 计算负载 | 实现现状 | OpenCV 能否/是否占优 | 结论 |
|---|---|---|---|
| 全图/窗口直方图统计（256-bin RGB，alpha/nodata 掩码） | 自研 `++hist[b][v]`（`exactStatsRGB`/`statsFromBuffer`，与 GDAL 块读流水） | `cv::calcHist` 需先把 GDAL 缓冲整理成 Mat（多一次拷贝/转换），多通道+掩码需 split/掩码参数，**反增内存与开销** | 自研更优 |
| 逐像素线性映射 `clip(g·x+o)` / LUT `lut[x]` | 自研简单循环（-O3 自动向量化） | `cv::LUT` 内部 SIMD/IPP **可能略快**——但该运算是纯带宽型，自研循环已接近内存带宽上限；且匀色应用非本项目瓶颈（远快于切片编码） | 收益≈0 |
| 重采样（near/bilinear/cubic/lanczos） | **全部委托 GDAL**（`GDALRasterIOExtraArg.eResampleAlg` / Warp） | GDAL 重采样与 nodata/掩码/坐标变换**强耦合**，OpenCV `cv::resize` 无法替代 | 不参与 |
| 图像编码（PNG/JPEG/WEBP） | **全部委托 GDAL**（libpng/libjpeg/libwebp 直通 + alpha + 地理标签） | OpenCV `imencode` 质量/体积不及 GDAL 直通，且无地理对接 | 不参与 |
| 平差解算（景级 gain/offset 最小二乘图平差） | 自研稀疏法方程 + 部分主元高斯消元（`solveLeastSquares`） | 未知数=等价类数（N=景数，≤数百）；OpenCV `cv::solve` 也是 LAPACK 封装，**此规模无实质差别** | 不占优 |
| 镶嵌融合（重叠区羽化/多带融合） | **未实现**（当前 vrt 用 ComplexSource 内联，无羽化） | 若做 Laplacian 金字塔融合，OpenCV `pyrDown/pyrUp/filter2D` **有明显价值** | 未实现，不构成当前依赖理由 |
| 采样填充 `sample_fill`（后期） | 未实现 | OpenCV `inpaint`/`distanceTransform` 可助力 | 后期 |

**辅助证据**：当前 `--as-needed` 已使链接器将 OpenCV 从产物剔除（`libip_color_balance.so`/`libip_tiling.so` 的 `DT_NEEDED` 无 opencv；dist/lib 39 个 so 中无 opencv）——即 OpenCV 从未真正进入运行时，此前仅为 **vcpkg.json/CMake 的声明冗余**。

**定稿结论**：**当前阶段不引入 OpenCV**。依赖最小化为 GDAL + nlohmann-json，减少依赖面、构建与部署复杂度（附加收益：分包体积与镜像体积更小）。

**再引入触发条件**（满足任一即重新评估，届时按需在 vcpkg 增加 `opencv4`）：
1. 实现**多带/拉普拉斯金字塔融合羽化**（`pyrDown/pyrUp/filter2D`）；
2. 实现 **`sample_fill` 采样填充**，需要 inpainting/距离变换等成熟算子；
3. **带宽型热点基准**（perf/nsight）证明 LUT/统计确为瓶颈，且希望用 IPP/SIMD 优化；
4. 具备 NVIDIA GPU 环境并决定落地 GPU 路径（`opencv4[cuda]`）。

### 4.2 Operator 接口设计（动态库，多接口面向不同业务）

```cpp
// 统一插件风格：工厂函数导出 + 纯虚接口，exe 通过 dlopen 或直接链接使用
class IImageOperator {
public:
    virtual ~IImageOperator() = default;
    virtual std::string name() const = 0;
    // 参数校验（不含 IO），失败给出可读错误
    virtual bool configure(const Params& p, std::string& err) = 0;
    virtual bool execute(const JobInput& in, const ProgressCallback& cb,
                          std::string& err) = 0;
};
// 每个 so 导出: create_operator() / destroy_operator()
```

**匀色 operator 提供四种业务接口**（同一套算法内核，输出形态不同，见 4.3/4.4）：

| 接口 | 输出 | 适用业务 |
|---|---|---|
| `balance_and_mosaic` | 物理镶嵌大 COG/TIF + 方案文件 | 需要归档一张成果大图的业务（原有模式，保留） |
| `balance_per_scene` | 每景匀色后 COG + 方案文件 | 无需镶嵌、单景分发/二次加工 |
| `balance_to_vrt` | **每景"匀色 VRT" + 镶嵌 VRT + 方案文件（零像素落盘）** | 默认工作流：直接接切片，省 TB 级磁盘与一次读写 |
| `apply_profile` | 按既有方案对影像解参/应用，输出其 VRT/COG。**实现**：`profile_mode=append`（新影像重叠区解参→输出新景 VRT→更新镶嵌 VRT→方案 JSON 追加）、`profile_mode=apply`（仅按既有方案冻结参数逐景输出，**不改方案**） | 新影像追加、服务化动态扩图（见 4.4） |

**切片 operator** 输入支持：COG/TIF、影像目录、**VRT（含匀色 VRT 与镶嵌 VRT）**；`tiles_scope=full|footprint` 支持增量切片。

- workflow exe 按配置串接以上接口（如 `balance_to_vrt` → `tiling`）；不做流式像素管线，避免复杂度。
- 物理输出模式中间格式用 **COG（deflate 或无损 webp）**：块组织对切片读友好，兼顾匀色结果的复用。

### 4.3 VRT 虚拟镶嵌模式（"匀色不落盘像素"——已本地实测验证）

**原理**：匀色变换参数不写像素，而是持久化进 VRT XML——每景生成一个"匀色 VRT"：`VRTDerivedRasterBand` + 像素函数引用方案参数，指向原始影像；再对 N 个匀色 VRT 做 `gdalbuildvrt` 镶嵌。切片引擎直接读镶嵌 VRT 的瓦片窗口，像素现算。

**实测结论（2026-10-12，conda GDAL 3.11.4，验证脚本 `scripts/phase0/verify_vrt_pixelfunc.py`）**：

| 验证项 | 结果 |
|---|---|
| 像素函数 gain/offset 数值正确性 | PASS（R 均值 67.4→102.2，理论一致） |
| VRT+像素函数窗口读取开销 | **0.96x，与直读同速**（Python 函数实测；生产用 C++ 注册函数更快） |
| 4 景镶嵌 VRT 跨景窗口读取 | PASS（27801×18538 镶嵌体） |
| 镶嵌 VRT + 外部金字塔(.ovr) 整图缩读 512×512 | 22ms（低 zoom 瓦片性能无虞） |

**实现要点与约束**：
- GDAL VRT **无内建 `<LUT>` 元素**（实测不生效，网上资料有误导），正确机制是派生波段像素函数；Phase 0 用 Python 内联函数（需 `GDAL_VRT_ENABLE_PYTHON=YES`），**生产 C++ 引擎用 `GDALAddDerivedBandPixelFuncWithArgs()` 注册带参函数**（参数经 `<PixelFunctionArguments>` 注入），无 Python 依赖、无 GIL。
- 像素函数可表达：景级线性变换（gain/offset）、**直方图匹配（256 项 LUT 同样可表达）**；**分块 Wallis 的逐像元参数场无法用 VRT 表达** → 开启 Wallis 精化的影像物理输出 COG，其余景仍可 VRT（混合模式允许）。
- 镶嵌 VRT 必须 `gdaladdo` 建外部金字塔（否则高层瓦片要读全分辨率数据，极慢）；.ovr 为低分辨率数据，空间远小于原影像。
- VRT 只读可多线程共享（每线程独立 dataset handle 即可）。
- 代价：切片时每窗口多做一次变换计算（实测近零开销）+ 每次部署需保证原始影像在位（VRT 是引用不是拷贝——归档时需连原影像一起归档，或改用物理模式）。

### 4.4 匀色方案文件（Profile）与增量生产

核心思想：**把"解算参数"与"应用参数"解耦；方案文件就是匀色的备份/存档/复用单元**。

方案文件（JSON，随成果归档，即"备份"）：

```json
{
  "profile_version": "1.0",
  "method": "overlap_adjust",
  "created_at": "2026-10-12T16:00:00+08:00",
  "target": {
    "type": "reference_image",
    "mean": [92.0, 92.3, 74.5],
    "std":  [21.0, 18.5, 20.3],
    "ref_histogram": null,
    "ref_image": "data/2024/H48E018014C.tif"
  },
  "images": [
    {
      "id": "H48E018014C",
      "source": "data/2024/H48E018014C.tif",
      "crs": "EPSG:4490",
      "footprint_wkt": "POLYGON((...))",
      "stats": {"mean": [81.3, 85.0, 67.0], "std": [20.3, 17.9, 18.4]},
      "transform": {"gain": [1.1, 1.05, 1.1], "offset": [3.0, 2.0, 4.0]},
      "balanced_vrt": "balanced/H48E018014C.vrt",
      "wallis_grid": null
    }
  ],
  "wallis": {"enabled": false, "block_size": 512}
}
```

关键设计：**target 统计（μ/σ 或参考直方图）固化在方案内** → 新影像对齐时**无需任何旧影像在场**（仅参考影像模式下建议保留 ref_image 以便复检）。

**新影像进入的三个场景**：

场景1——批处理追加（`profile_mode=append`）：

```
载入方案 → 新影像统计(排除nodata) → 解参（依 Phase 0 §4.6 补验结论）：
  - 新影像与既有影像有重叠（主路径）：用重叠区统计解参（景级 gain/offset）
    → 接边一致性检查：|Δμ|<阈值(默认2) 的对自动跳过调节
  - 完全无重叠（回退）：与方案 target 统计对齐，日志提示接缝风险
  → 生成新影像匀色 VRT → 更新镶嵌 VRT（gdalbuildvrt 重跑，秒级）
  → 增量切片：仅重切 [新影像 footprint ⊕ N 瓦片缓冲] 覆盖的 z/x/y
  → 方案 append 新记录 → 保存（版本化，即备份）
```

场景2——服务化新增影像（`apply_profile`）：服务持有方案文件（本地/DB/对象存储），新影像到达即按场景1流程处理；**方案一旦冻结不再变，历史瓦片色彩恒定，新瓦片向同一基准对齐**。此架构下"瓦片匀色"转化为"同一方案的一致应用"，**不需要对瓦片做二次匀色**——这正是"先栅格匀色后切片"在增量场景的正确延伸。

场景3——全局重算（`profile_mode=recreate`）：新旧全体重统计、重解参数、全量重切。仅业务基准变更时使用，默认不用。

**方案备份与追溯**：方案文件为纯 JSON（+可选 Wallis 参数栅格小文件），建议双写——切片成果根目录（`tiles/_profile.json`）与匀色成果目录各一份，任一瓦片可追溯到生成它的方案版本。

### 4.5 服务化路线（需求 7）

- **cpp-httplib 足够**：HTTP 层很薄，瓶颈在处理本身。架构：HTTP 前端进程只做任务接收/排队/状态查询，通过 fork/exec 或 unix socket 派发 **worker 子进程**执行 operator —— 单任务崩溃不影响服务（这正是你说的多进程隔离动机）。
- **不需要 Go**：Go 的优势（协程、容器镜像小）对本场景无决定性收益，反而引入双语言、双依赖管理（GDAL 绑定仍需 cgo/swig 回到 C++）。C++ 内用"1 个调度进程 + N 个 worker 进程"即可获得同等隔离性。
- **Docker**：纯 CPU C++（GDAL+OpenCV）镜像完全友好（debian/gcc runtime 基础镜像约 200MB 级），无 GUI/驱动依赖；当前唯一潜在问题是 GDAL 对容器内 CPU/内存探测（无实质影响）。此项列入 Phase 4，不影响前期设计。

## 七、已确认决策（2026-10-12 与需求方讨论确认）

1. **切片坐标系**：三种方案全部支持 —— WebMercatorQuad (3857) / CGCS2000 (4490，天地图规范，层级从 1 起) / WorldCRS84Quad (4326)，默认 WebMercatorQuad；另支持任意自定义 tms json。

3. **输出格式默认值**：`format=png` + `nodata_mode=transparent`（无效区透明 PNG）；WebP/JPEG/填充/采样填充均参数可调。
4. **GPU**：本期纯 CPU（多线程 + SIMD 为主），接口与编译开关（`use_gpu` 参数、CMake option）预留，待有 GPU 环境再实现。
5. **MBTiles/GPKG 打包**：列入后期（Phase 4 之后按需），本期实现目录式 XYZ/TMS 结构。
6. **匀色输出多接口**（2026-10-12 新增需求确认）：物理镶嵌 COG（原有业务保留）、每景 COG、**匀色 VRT+镶嵌 VRT（推荐默认，零像素落盘，已实测验证）**；切片引擎支持 VRT 输入。
