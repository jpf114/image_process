## 二、Phase 4 服务化设计（方案 §4.5 细化）

> **前置论证见 [Phase4服务化论证报告.md](Phase4服务化论证报告.md)**（2026-10-13）：cpp-httplib + 1 调度进程 + N worker(fork/exec) 判定为可行且成熟（Gunicorn sync worker 同范式），须落实 8 项工程约束——尤其 ①长任务不得占用 HTTP 线程 ②GDAL 官方禁止叉在 GDAL 操作中途，worker 必须 fork+exec ③容器内显式指定线程数（cgroup CPU 探测失真）④内存决定 worker 并发上限；无需 Redis/Celery（内存队列 + 磁盘 JSON 原子写即可）。

### 2.1 架构
```
┌────────────┐   HTTP    ┌──────────────────┐  fork/exec  ┌─────────────┐
│ 客户端      │ ────────▶ │ ip_server (cpp-  │ ──────────▶ │ worker 进程  │
│ (提交/轮询) │ ◀──────── │ httplib, 薄层)    │  任务JSON    │ (workflow/  │
└────────────┘  状态/结果 │  - 任务队列(内存) │             │  单 operator)│
                          │  - worker 池管理  │ ◀────────── │  独立崩溃隔离│
                          │  - 静态瓦片预览   │  状态回写     └─────────────┘
                          └──────────────────┘
```
- **进程模型**：1 调度进程 + N worker（默认 = 内存允许的并发数，遵守 MemGuard）；worker 崩溃不影响服务（多进程隔离动机落地）
- **任务**：JSON（与 workflow 配置同构）→ 队列 → worker 执行 → 状态机（queued/running/done/failed）+ 进度百分比（operator ProgressCallback 已具备）
- **接口**（REST，v1）：
  - `POST /api/v1/jobs`（提交，返回 job_id）
  - `GET /api/v1/jobs/{id}`（状态/进度/日志尾部）
  - `GET /api/v1/jobs/{id}/logs`（运行日志——**日志落盘能力已具备**）
  - `DELETE /api/v1/jobs/{id}`（取消）
  - `GET /tiles/...`（静态瓦片服务，映射输出目录）
- **依赖**：cpp-httplib（header-only，vcpkg 有，**加装需征得同意**）；无 DB（任务队列内存 + 磁盘 JSON 状态文件，重启可恢复）
- **Docker**：debian-slim 基础镜像 + dist 包（package_release.sh 产物）+ EXPOSE；无 GUI/驱动依赖，纯 CPU 友好（方案 §4.5 已确认）

## 三、MBTiles/GPKG 打包（S4，已完成）

> **状态：✅ 完成（2026-10-13）**。实现与最初调研的差异：**未采用"逐瓦片 INSERT 自建 SQLite"**，
> 改为复用 GDAL 内置 MBTiles / GPKG 驱动的 `Create` + 逐瓦片块写（实测 `DCAP_CREATE=YES`），
> 无需新增 sqlite3 依赖、包结构与规范一致由驱动保证。三条实测硬约束见 AGENT.md §8.16~18。

- **MBTiles**：SQLite 单文件（`tiles(zoom_level,tile_column,tile_row,tile_data)` 唯一索引）；规范限定**全球墨卡托**，故 `package=mbtiles` 仅允许 `tiling_scheme=WebMercatorQuad`（配置期即拒绝其它方案）
- **GPKG**：OGC 标准，任意 TMS 均可；`TILING_SCHEME` 由当前 `TileMatrixSet` 现场导出为 OGC TMS JSON（`_tmp/tiling_scheme.json`），`gpkg_tile_matrix` 一次登记 0..max 全层级
- **实现**：tiling 加 `package=mbtiles|gpkg`（+ `package_file`）参数；渲染管线复用——worker 照常渲染像素块，经包 sink 一次 `RasterIO` 整块写入（块索引 = 瓦片编号）；不再落散文件
- **增量追加**：包文件已存在且未 `overwrite` 时按追加打开，瓦片写入走 UPSERT（`INSERT OR REPLACE` 语义），与断点续跑语义一致
- **验证**：验收矩阵 E 组 7 项——包内瓦片与散文件**逐像素最大差 0**；`minzoom/maxzoom`、`gpkg_tile_matrix`、`gpkg_tile_matrix_set` 均正确；同 bbox 二次运行瓦片数不变、相邻 bbox 1→2
- **限制**（已文档化）：打包模式 `tile_size` 固定 256（包内瓦片矩阵按 256 定义）；包内 `zoom_level` = TMS 矢量索引（CGCS2000 为「目录层级 − 1」）；GPKG 追加到**更深层级**需该层级已在 `gpkg_tile_matrix` 中登记（建包时以最深层级 Create 即可覆盖）

## 四、多景按景并行（S5，已完成）

> **状态：✅ 完成（2026-10-13）**。语义按参数原注释落地：`input` 为目录 → 按景并行。

- **归属**：编排在 `apps/`（`scene_fanout`，tiling 与 workflow 共用）；`iptl::ITiling` 保持单输入语义、不做进程管理（与 Phase 4「operators=算法、apps=编排」一致）
- **进程模型**：`num_processes<=1` 本进程逐景串行；`>1` 维护最多 N 个子进程（完成一个补一个），子进程 = 与当前可执行文件同目录的 `workflow --config <每景参数 JSON> --only tiling`
- **参数传递**：`tilingParamsToJson/FromJson`（唯一来源，gtest 锁死全字段往返）——不重建命令行，避免漏字段导致子任务行为漂移；workflow 的切片段解析亦收敛到该入口
- **输出布局**：每景 `<output_dir>/<场景名>/…`（同名场景加 `_2`）；临时 `_fanout/*.json` 用后清理
- **线程分摊**：未显式指定 `num_threads` 时每景 = `核数/进程数`（避免超订）
- **失败语义**：单景失败不影响其余景，汇总后返回非 0
- **验证**：验收矩阵 F 组 6 项——3 景下多进程与串行**逐像素最大差 0**；失败归集（1 波段景）退出 1 且其余 2 景产出；workflow 目录输入同路径通过
- **顺带修复**：独立 `tiling` CLI 读每景匀色 VRT（`ip_gain_offset` 未注册）必然失败 → 现已幂等注册（AGENT.md §8.20）
